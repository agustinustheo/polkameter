Load and stress testing
for Polkadot SDK chains

A JMeter-style workbench: an XML plan, runtime plugins and one Rust engine

About 15 minutes. Why chains need their own load tool (2 min), what Polkameter is (2 min), one run end to end (4 min), how the result is judged (4 min), architecture and how to start (3 min).

The problem

“Accepted” is not “included”

HTTP load tools

Count replies

A 200 OK means the work is done. Throughput is requests per second and latency is time to reply.

A blockchain

A reply is a promise

The node accepts a transaction into its pool. It may be included later, refused, dropped, put on a fork that loses, or simply never seen again.

So we must

Follow every transaction

To the best block, to the finalized chain and back to the pool, and only then say how much the chain really carried.

The limits are also elsewhere: the transaction pool, block building time, finality and, for a parachain, the relay chain backing its blocks.

The core idea of the tool. A generic load tester would report the submit rate. Polkameter reports what was included, how fast, and accounts for every transaction that was not.

What it is

JMeter’s model, for Polkadot SDK chains

Declarative

An XML plan

Steps, workflows, the load shape, monitors and thresholds. Validated before anything touches a chain.

Runtime-specific

Plugins

Separate executables that prepare transactions and check runtime state. The core never builds a runtime call.

Chain-agnostic

One Rust engine

Submits at a controlled rate, follows blocks, reconciles every transaction, scrapes nodes, judges the run.

Front end

polkameter CLI

Headless, for CI and load machines. --format json for machines.

Front end

Desktop app

Tauri. Edits and runs the same plans.

Front end

Remote agent

Runs plans on a host with its own plugins and secrets, over TLS or a loopback tunnel.

Three parts and three front ends. All three front ends drive the same engine, so a plan that validates on a laptop behaves the same on a remote load machine.

The plan

<?xml version="1.0" encoding="UTF-8"?>
<polkameter-plan xmlns="https://polkameter.dev/schema/plan"
    version="1" name="Plugin data flow" timeout-ms="30000">
  <plugins><plugin id="example" version="0.1.0" protocol="1"/></plugins>
  <setup>
    <step id="seed" use="example.double">
      <input name="value" value="21"/>
    </step>
    <step id="copied" use="core.echo">
      <input name="value" ref="steps.seed.value"/>
    </step>
  </setup>
  <workflow id="users" users="3" iterations="2" concurrency="2">
    <step id="computed" use="example.double">
      <input name="value" ref="steps.copied.value"/>
    </step>
    <step id="verified" use="core.assert-equal">
      <input name="actual" ref="steps.computed.value"/>
      <input name="expected" value="84"/>
    </step>
  </workflow>
</polkameter-plan>

Plans say what, not how

  • use="plugin.operation" picks a step from an installed plugin or core.
  • Inputs are a literal value or a ref to an earlier output: steps.ID.OUTPUT, targets.ID, run.id.
  • Forward references and unknown outputs fail before setup; malformed XML and unknown elements or attributes are reported with a line and column.
  • Plans name a credential profile and a topology alias, never a secret or a path.
This is the example plan that ships in the repository and runs without a chain. A real stress plan adds a load element with targets, rates or a ramp, monitors and thresholds.

One run

Every run follows the same order

3Setup

→
5aBaseline
→
5bLoad steps
→
5cRecovery
→
5dFinality wait & reconcile
→
6Evaluate
→
7Report & checks
→
8Teardown, always

Blue is the measured load. Setup time is excluded from it. Teardown runs even when preflight, setup, a workflow or the load fails.

Preflight is read-only: it checks installed plugins, required metrics and calibrates the block interval. The measured part has four stages. Baseline sends a few probes before load to know the normal latency. Recovery keeps probing after the load stops until a run of probes lands in time again.

The load

Step the rate up, find the onset

step 0
2 tx/s
step 1
4 tx/s
step 2
6 tx/s
step n
onset

Fixed rates, a linear ramp (step) or a geometric one (growth). Prepared transactions go out over several WebSocket connections.

A step fails by default when:

  • fewer than 90% of its transactions are included,
  • p95 send-to-inclusion latency exceeds 10 s, or
  • more than 1% of submissions are refused.

The first failed step is the failure onset; the last good one is the max sustained rate. Stalled blocks or finality, or a flood of pool refusals, stop the load early. The limits are <thresholds> attributes.

Other stop rules: block production stalls, finality stalls, block gaps over twice the expected interval, and the load tool itself not keeping up, which ends the run without blaming the chain.

Loss accounting

Every transaction is accounted for

included
refused
still ready
unknown
lost

Tracked live

Replies and best blocks, per transaction, while the load runs. The pool is read once the load and recovery are over.

Reconciled on finality

After the finality wait every transaction is checked against the finalized chain: those the tracker missed, those only on a fork and those moved to another block.

Lost means lost

Accepted, in no block, with no error and not in the pool. A healthy chain must show zero.

This is what makes the result trustworthy. The statuses are exclusive, so the counts add up to the number sent. A transaction that failed inside its block still counts as included and is flagged as failed. The pool check is “no silent loss”.

Monitors

Watching the nodes, not just the client

Nodes

Prometheus scraper

Collator and validator metrics from the network’s topology: block build time, pool validations, ready transactions and why blocks ended.

Parachains

Relay observer

Follows the relay chain for the parachain’s slots: offered, backed, included, timed out, and disputes.

Node under load

Process sampler

CPU and memory of the node process that receives the load, sampled with ps.

Each monitor writes its own raw file. The checks read the recorded series afterwards, so polkameter report can judge a run again from its files alone.

Monitors are configured by the plan’s monitors element: a topology alias registered on this host, the para id and the relay target. Plugins can add observers and checks too.

The verdict

Outcome checks turn series into a verdict

OutcomeChecks
Block productionwhy blocks end · build time within the authoring deadline
Poolno silent loss · the burst drains · refusals are clean · pool work leaves time for blocks
PVFrelay slots · no timed-out candidates or disputes · PVF time on validators · collation funnel
Runmonitors recorded everything
Pluginstheir own checks, returned from evaluate steps (required or optional)
Pass

The rate cap was reached and no check failed or warned.

Warn

Nothing failed, but a check raised a warning.

Fail

A load step broke a response criterion, or a check failed.

Inconclusive

The load stopped early without a failure onset, or a required check had no result.

The verdict is in the report; the exit code is separate. In smoke mode a monitor problem or a required check without a result makes the process exit nonzero, which is what CI wants.

A real report

A smoke run, as Polkameter wrote it

Verdict: FAIL. Failure onset at step 0: p95 send to best block was 23.1 s against a 10 s limit.

Loss check: 360 sent, 360 included, 0 refused, 0 lost, all confirmed on the finalized chain.

Recovery: back 1 s after the load stopped; a backlog of 37 drained in 7 s.

Everything was included, yet the run fails on latency at the very first step. The report says which criterion failed and where.

These numbers come from the smoke run kept in the repository as a test fixture; the replay test recomputes its checks and loss figures from the raw files.

Small crates around one engine

Front ends
CLIvalidate · preflight · run · report · plugin · agent
DesktopTauri app on the same engine

Orchestration
engineplan parsing and validation, plugin host, step executor, measurement wiring, artifacts
Measurement

Contracts
filesthe run directory, metric registry, recorded series
plugin-sdkJSON protocol over stdio for plugin authors
Dependencies point downward. files is the on-disk contract shared by the writers (load, monitors) and the reader (checks), which is why a run can be judged again offline.

Plugins

Runtime knowledge lives outside the core

Manifest

Operations with typed input and output schemas, requirements (capabilities, RPC, metrics).

Protocol

JSON requests and responses over stdin and stdout. Any language can implement it.

Pinned

plugin install records the version and a BLAKE2 hash of the executable.

Scoped

Credentials and topologies are mapped per host; plans only name them.

A plugin prepares the transactions a load submits, checks the state they should leave, and can return its own outcome checks.

The core does the rest: rate control, tracking, reconciliation, monitoring and the verdict, the same way for every chain.

The example plugin in plugins/example uses polkameter-plugin-sdk and runs without a chain.

The People chain plugin lives in the polkadot-pop-e2e repository and is installed without rebuilding Polkameter. A modified executable no longer matches its pin and is refused.

Getting started

From a clone to a run directory

# the CLI only: from crates.io, or from this checkout
cargo install polkameter
cargo build -p polkameter --bin polkameter
cargo build -p polkameter-example-plugin

polkameter plugin install target/debug/polkameter-example-plugin
polkameter validate examples/plugin-workflow.polkameter.xml
polkameter run examples/plugin-workflow.polkameter.xml --output runs
polkameter report runs/run-<id>

samples.jtl

JMeter CSV of every step.

events.jsonl

The run as events.

summary.md

The report above, plus summary.json.

transactions.jsonl

Every transaction’s fate.

scripts/local-fork-run.sh runs a plan on a fresh local Zombienet network. In CI, smoke mode exits nonzero when a monitor fails or a required check has no result.
